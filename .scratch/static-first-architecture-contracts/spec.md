# Static-first architecture contracts

**Status:** ready-for-agent

## Problem Statement

The template currently proves that its Astro, i18n, design-token, and SEO
foundation builds, but several important architectural contracts still live as
component-local implementation details. Metadata is assembled inside a layout,
locale URL behavior is partly duplicated, design values are available only as
CSS, and invalid static-generation state does not have a single structured
failure mechanism. Internal import aliases expose the entire source tree instead
of defining intentional module boundaries.

This makes future projects more likely to accumulate implicit environment reads,
hardcoded head values, ad hoc validation, and tests at the wrong seam. It also
makes pure UI harder to develop in isolation while encouraging layouts and pages
to be treated like ordinary components even though their behavior depends on the
Astro rendering environment.

## Solution

Establish a static-first architecture in which design values have both CSS and
build-time JSON representations, page-head derivation is a pure functional
module, locale and component APIs are explicit, and invalid SSG state fails the
build through structured contracts. Use Storybook Astro as the isolated
workbench for pure UI components, while rendering layouts and pages in colocated
Vitest tests. Replace the catch-all source alias with narrow package import maps
that describe supported implementation boundaries.

The resulting template should make the correct path the shortest path: UI is
developed through stories, page-shell behavior is verified at rendered seams,
design metadata comes from DESIGN.md, and states that cannot produce a valid
static site stop the build with actionable diagnostics.

## User Stories

1. As a project developer, I want DESIGN.md to remain the only source of design values, so that browser metadata and CSS cannot drift apart.
2. As a project developer, I want design tokens exported as DTCG JSON, so that server-side Astro code can consume them during static generation.
3. As a project developer, I want generated design JSON excluded from version control, so that generated artifacts never create cleanup commits.
4. As a CI user, I want design CSS and JSON regenerated before checks and builds, so that a clean clone is always valid after installation.
5. As a CI user, I want malformed or incomplete generated token data to fail immediately, so that invalid design state cannot reach deployment.
6. As a site visitor, I want browser theme metadata to match the design system, so that browser chrome does not use a stale hardcoded color.
7. As a page author, I want to pass already translated title and description strings to the layout, so that the layout is independent of translation infrastructure.
8. As a page author, I want a small page-head input contract, so that I do not repeat title, canonical, image, robots, and social metadata logic.
9. As a maintainer, I want page-head derivation to be a pure function, so that it is predictable, composable, and easy to test.
10. As a maintainer, I want the layout to render a prepared head model, so that presentation and metadata derivation do not become entangled.
11. As a localization developer, I want locale passed explicitly into components and layouts, so that reusable modules do not depend on hidden Astro globals.
12. As a site visitor, I want the document language to use a valid BCP 47 language tag, so that browsers and assistive technologies interpret it correctly.
13. As a localization developer, I want alternate URLs generated by Astro's native i18n API, so that link behavior follows the configured routing policy.
14. As a component author, I want every component to expose its Props type and public constants, so that consumers and tooling can share its public contract.
15. As a component author, I want existing component folder and index conventions preserved, so that architectural work does not trigger unrelated file moves.
16. As a UI developer, I want pure UI components represented by colocated stories, so that visual states can be developed and reviewed in isolation.
17. As a UI developer, I want Storybook to use the real Astro and design configuration, so that stories resemble production rendering.
18. As a UI developer, I do not want boilerplate unit tests for markup-only components, so that tests focus on meaningful behavior.
19. As a page developer, I want layouts and pages covered by rendered tests, so that document structure, head metadata, and environment integration are verified.
20. As a TDD practitioner, I want pure library tests colocated with their modules, so that implementation can proceed through small behavioral feedback loops.
21. As a build operator, I want invalid SSG state to terminate the build, so that failures happen before deployment rather than in a visitor's browser.
22. As a build operator, I want contract failures to include a stable code, context, cause, and stack, so that failures are understandable without reproducing them interactively.
23. As a build operator, I want optional build traces for contract execution, so that CI failures can be correlated without requiring an observability backend locally.
24. As a privacy-conscious developer, I want telemetry disabled or no-op by default, so that the template never sends build data unexpectedly.
25. As a coding agent, I want narrow import-map names that express architectural roles, so that I can discover supported boundaries without knowing physical paths.
26. As a maintainer, I want unsupported source paths hidden behind package imports, so that internal reorganization does not rewrite every consumer.
27. As an editor user, I want Astro, TypeScript, Vitest, Storybook, ESLint, and language servers to resolve the same imports, so that feedback is consistent across tools.
28. As a developer, I want internal import specifiers without file extensions, so that imports express module identity rather than storage format.
29. As a maintainer, I want framework environment APIs visually distinct from internal modules, so that hidden environmental coupling is easy to review.
30. As a template user, I want one complete quality command to verify generation, contracts, stories, tests, and the static build, so that local and CI behavior stay aligned.

## Implementation Decisions

- DESIGN.md remains the sole source of design-token values and intent.
- The pinned design CLI exports both Tailwind-compatible CSS and DTCG JSON.
  Generated outputs are disposable, ignored, deterministic, validated, and
  replaced atomically.
- Design generation runs during installation preparation, before checks and
  builds, and in watch mode during development. A clean checkout must not depend
  on committed generated files.
- The DTCG output exposes a named browser-theme color token as part of its
  validated public contract. The layout imports the generated JSON in Astro
  frontmatter during SSG and serializes the resolved value into theme-color
  metadata. The JSON is not delivered as a client runtime dependency.
- Page-head derivation uses a pure functional API. It receives constituent data
  and returns an immutable head model; no class, mutable builder, or component
  lifecycle is involved.
- Title and description inputs are translated strings. The head model and layout
  do not receive translation keys and do not call i18next for these values.
- The head model owns derivation such as full title, canonical URL, social image
  URL, robots policy, card type, and browser theme color. The layout owns only
  document composition and rendering.
- Open Graph metadata uses property and content attributes. Twitter metadata uses
  name and content attributes. Each emitted social meta element has exactly the
  two attributes required by its protocol.
- Locale is an explicit prop for reusable components and layouts. Reusable
  modules do not read the current locale from Astro implicitly.
- The document layout renders a validated BCP 47 language tag. Conversion from a
  route locale identifier to a language tag happens at an explicit boundary.
- Locale-alternate links are rendered by a dedicated head component and generated
  with Astro's native relative-locale URL API.
- Every Astro component and layout exports its Props type and any public constant
  it declares. The ESLint rule that prohibits component exports is disabled
  intentionally and documented as part of the project contract.
- Existing component organization is preserved. This work does not introduce,
  remove, or normalize component directories, colocated companion files, barrel
  files, or index modules merely for structural consistency.
- Pure UI components use colocated Storybook stories as their primary executable
  examples and UI-state verification. Markup-only components do not receive
  Vitest files by default.
- Storybook Astro is limited to pure UI. Stories receive translated content,
  locale, and other environment-derived values through args rather than using
  routing, page, layout, content-collection, or native i18n behavior.
- Layouts and pages are outside the Storybook contract. They use colocated
  rendered tests against the Astro rendering environment.
- Pure library modules continue to use colocated Vitest tests when their behavior
  is developed through TDD.
- SSG contracts are production build-time functionality, not in-source tests.
  They express states that must be true for a valid static artifact.
- Failed SSG contracts accumulate diagnostics and may recover with explicit
  collection contracts so independent static derivation can continue. Recovery
  never clears a diagnostic; the build throws one aggregate at its boundary.
- Contract diagnostics include a stable machine-readable code, a human-readable
  message, route or component context where available, the original cause, and a
  useful stack trace.
- SSG contracts expose a narrow observability seam. The default reporter is local
  and requires no network or collector. An optional OpenTelemetry adapter can
  create spans and events, record exceptions, mark spans as errors, and flush or
  shut down cleanly before the finite build process exits.
- Telemetry export is opt-in and configured outside source control. The template
  does not ship credentials, a mandatory backend, or silent network export.
- Internal module boundaries use narrow package import maps grouped by role, such
  as components, layouts, localization, libraries, and styles. A catch-all import
  exposing the complete source tree is not allowed.
- Package import maps are introduced after the other architectural changes have
  landed, avoiding path migration churn while modules are still moving.
- Astro, TypeScript, Vitest, Storybook, ESLint, and supported editors must resolve
  the same package import maps. Legacy path aliases are removed only after every
  consumer has migrated.
- Internal package import specifiers are extensionless. Source code does not add
  `.ts`, `.js`, `.astro`, or another storage extension to an internal module
  name; the import-map target owns the physical extension where one is required.
- Import-map entries may use subpath patterns or explicit entries, but must not
  change the existing component organization merely to make a wildcard mapping
  convenient.
- Framework and environment APIs use named imports. Internal independent modules
  use namespace imports. Astro components use default imports. Type-only imports
  follow the same distinction, and ESLint enforces the convention.
- The custom recursive TypeScript translation-key machinery is replaced by types
  generated by the official i18next CLI. Runtime translation-catalog validation
  remains a separate concern and is not removed merely because types are
  generated.

## Testing Decisions

- The highest acceptance seam is the repository's complete quality command. It
  must generate both design artifacts, validate their contracts, build
  Storybook, run Vitest, type-check the Astro app, and complete a static build.
- Design generation is tested through its public output contract. Tests assert
  that valid DESIGN.md input produces both CSS and DTCG JSON, required tokens are
  present, invalid input fails, and replacements cannot leave partial output.
- The functional page-head module is tested as a pure public transformation.
  Tests use translated strings and URL inputs and assert only returned behavior,
  not helper calls or internal branches.
- Layout tests render the real layout through Astro's server-side container or an
  equivalent rendered seam. They verify document language, canonical metadata,
  alternate links, theme color, title, description, Open Graph attributes, and
  Twitter attributes.
- Page tests render representative default-locale and non-default-locale pages.
  They verify the complete handoff from page inputs to rendered layout output.
- A deliberately invalid static-render fixture exercises the SSG contract at the
  build boundary. The observable contract is a non-zero build, all independent
  diagnostics, stable codes, readable context, preserved causes, and conspicuous
  recovery reaching later derivation.
- OpenTelemetry behavior is tested through the reporter seam with an in-memory
  implementation. Tests verify error status, exception recording, and flushing;
  they do not require a real collector or network access.
- Pure UI components are represented by colocated stories covering meaningful
  states, accessibility-relevant variations, and supported props. The static
  Storybook build is the baseline verification for these stories.
- UI components receive standalone Vitest tests only when they acquire non-visual
  behavior that cannot be expressed adequately through stories.
- Layouts and pages do not use Storybook as a substitute for Astro rendering
  tests.
- Pure library tests and layout/page tests are colocated with their subjects.
  Existing design-generator and localization-boundary tests are the prior art for
  testing public seams rather than implementation details.
- Import-map verification runs across all consuming tools. Passing TypeScript
  alone is insufficient if Storybook, Vitest, ESLint, Astro, or editor resolution
  still requires a private path alias.
- Import-map tests and linting verify that every supported internal import works
  without a file extension in its source specifier. Resolution must not depend on
  one tool silently appending an extension that the other tools cannot resolve.

## Out of Scope

- Changing the existing component directory, companion-file, barrel, or index
  organization.
- Requiring a Vitest file for every Astro UI component.
- Rendering layouts, pages, native routing, or content collections in Storybook.
- Using Storybook as the application end-to-end test runner.
- Replacing Astro's static output with SSR or adding a deployment adapter.
- Silently recovering from invalid SSG state or treating recovered build output
  as a successful production artifact.
- Guaranteeing that build-time contracts can detect states that are neither
  rendered during SSG nor expressed as explicit invariants.
- Requiring an OpenTelemetry collector, vendor account, remote exporter, or
  telemetry credentials.
- Shipping generated design JSON to browser JavaScript solely to populate head
  metadata.
- Introducing a class-based page-head builder.
- Exposing the entire source tree through a catch-all package import.
- Redesigning the translation runtime, locale catalog format, or translation
  content as part of replacing the TypeScript typing layer.

## Further Notes

- Embedded SSG contracts, Vitest tests, and Storybook stories are three distinct
  mechanisms. Contracts protect artifact validity, tests drive and verify
  behavior, and stories describe isolated UI states.
- OpenTelemetry augments diagnostics but never replaces thrown errors. The local
  CLI report and stack trace remain the primary failure experience.
- DTCG JSON is preferred over a Tailwind-specific JSON representation for
  server-side consumers because it preserves a tool-neutral design-token model.
- Import-map migration is intentionally last. The final map should describe the
  architecture produced by the preceding work rather than preserve obsolete
  physical paths.
